Counting Sort

Skip comparisons entirely — count how many times each value appears, then use those counts to place every element directly into its final position.

The Problem

You need to sort n integers, and every one of them is known to lie in a small range [0 .. r], where r = O(n).

Every comparison-based sort (Selection, Merge, Quick, Heap Sort) is bound by Ω(n log n) in the worst case — that's a proven lower bound for any algorithm that only compares elements. But if you already know something extra about the data (like its range), you can sometimes do better by not comparing at all.

Think About It

Before reading further: if you knew there were exactly 2 zeros, 0 ones, and 2 twos in a list, could you figure out exactly which output positions the zeros belong in — without ever comparing them to anything else?

What if you kept a running tally, "how many elements are ≤ this value," for every possible value?

Now Let's See the Real Algorithm

Input: array A[1..n] of integers, each in [0, r] with r = O(n).

Output: array B[1..n], the elements of A in sorted order. Auxiliary: array C[0..r] for counting.

Core idea

For each element x, determine the number of elements ≤ x — that number directly tells you x's final position in the sorted output. No pairwise comparisons needed at all.

Step 1. Count occurrences: for each value i, count how many times it appears in A.
Step 2. Accumulate: turn those counts into cumulative sums, so C[i] now means "number of elements ≤ i."
Step 3. Place: scan A from the last element to the first; place each A[j] at position C[A[j]] in B, then decrement C[A[j]] so the next equal value lands one slot earlier.

Pseudocode

COUNTING-SORT(A, B, n, r) 1. for i ← 0 to r 2. do C[i] ← 0 3. for j ← 1 to n 4. do C[A[j]] ← C[A[j]] + 1 5. ▷ C[i] contains the number of elements equal to i 6. for i ← 1 to r 7. do C[i] ← C[i] + C[i-1] 8. ▷ C[i] contains the number of elements ≤ i 9. for j ← n downto 1 10. do B[C[A[j]]] ← A[j] 11. C[A[j]] ← C[A[j]] - 1

How Efficient Is It?

CaseTime ComplexityWhy
Best / Average / WorstΘ(n + r)Every phase is a single linear pass — over A (size n) or over C (size r+1) — with no data-dependent branching cost.

In practice, Counting Sort is used exactly when r = O(n), which makes the running time Θ(n) — genuinely linear, beating the Ω(n log n) lower bound that applies to any comparison-based sort (which this isn't).

Space complexity: O(n + r) — the counting array C and the output array B are both extra space; Counting Sort is not an in-place sort.

Stability: Counting Sort is stable — scanning A from n downto 1 in the placement step ensures that when two elements have equal value, the one that appeared earlier in A also appears earlier in B.

When Would We Use It?

  • When elements are integers (or map cleanly to integers) within a range that's not much bigger than n — e.g. exam scores 0–100, ages, small counts.
  • When you need a stable sort, especially as a subroutine — Radix Sort relies on exactly this property.
  • Avoid it when the range r is much larger than n (e.g. sorting 100 arbitrary 64-bit integers) — the Θ(r) term would dominate and make it slower than a comparison sort.

Common Mistakes

Using it outside its assumptions

Counting Sort only works on non-negative integers in a known, bounded range. It can't directly sort floats, strings, or arbitrary-range integers.

Scanning A forwards in the placement step

Placing elements in the order j ← 1 to n instead of n downto 1 still produces a sorted array, but breaks stability — equal elements would end up reversed relative to their original order.

Forgetting to decrement C[A[j]] after placing

Without the decrement, every occurrence of a repeated value would try to write to the exact same position in B, overwriting earlier placements.

Confusing the two roles of C

C starts as a simple frequency count, then is overwritten in place to become cumulative sums — it's easy to forget these are two different meanings of the same array at two different points in the algorithm.
